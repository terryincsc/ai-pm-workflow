# 任務分類：只有符合條件才是小改

只有兩種流程：**小改／一般功能**。PM 先判斷是否同時符合下列全部條件及一個已列案例；任何一項不符合、未知或未列入，就走一般功能。不依行數、檔案數、預估工時或「看起來簡單」判斷。高風險只影響拆分、選模與驗證，不另設「複雜」流程。

## 小改的必要條件（全部符合）

1. 使用者要的結果與修改位置已明確，沒有待決設計或根因調查。
2. 局部且可列出全部受影響範圍，不改共用介面、資料結構、依賴、建置／部署或協作政策。
3. 不增加或變更業務規則、流程、權限、帳務、交易、資料寫入／刪除、併發及安全行為。
4. 不涉及既有資料修正、遷移或一次性資料執行。
5. 有明確可觀察的驗收方式及受影響回歸項目；可局部回退。
6. **符合下表某個已列案例的完整邊界**，在規劃書記錄案例 ID 與逐項理由。

## 初始允許案例

採以下保守範圍試行；不是「類似就算」。

| ID | 可視為小改 | 排除情況 | 驗證 |
|---|---|---|---|
| S01 | 已定位的畫面錯字、標點、純顯示標籤修正 | 改變操作含義、條款／金額／權限／錯誤承諾、識別 key、翻譯架構 | 顯示正確、原操作與相關畫面不受影響 |
| S02 | 單一局部元件的間距、顏色、字級調整，明確給定目標 | 共用樣式、響應式／互動行為變更、降低可讀性或無障礙能力 | 指定畫面及既有支援尺寸檢查 |
| S03 | 文件錯字、排版或已知正確目標的失效連結修復 | 修改需求、協作規則、權限、指令語義、設定或架構 | diff、連結與內容含義一致 |

## 兩種流程的差別

| 項目 | 小改 | 一般功能 |
|---|---|---|
| 規劃書 | 同一 NNN 檔，可短寫需求、分類依據、可動／不碰、驗收／回歸及派工紀錄 | 完整範圍清單與任務拆分 |
| 分析 RD | 條件已明確通常不需要；若需探索則重新分類 | 有未知技術問題時派唯讀 rd_architect |
| 實作 | 通常 rd_mechanical；實際按任務選模 | rd；疑難除錯用 rd_debugger |
| 測試撰寫 | 無需新增測試時可省略 test_writer；必要測試須明確指定作者 | 產品功能預設 test_writer；純文件／設定不需測試碼時可省略並記原因 |
| 共同關卡 | 使用者確認範圍 → 實作／自測 → 全新 Reviewer → 全新 Tester → PM 報告／PR → 使用者 merge | 相同，不因分類更改驗收責任 |

PM 不因「小改」自動省略必要測試、獨立驗收或既有授權關卡。執行中出現未知影響或不符條件，改列一般功能；已核准且未變的範圍無須重複確認，新增範圍仍由使用者決定。

## 試行與增補

- PM 判一般功能、使用者認為是小改時，先核對必要條件第 1–5 項全部符合，再由 PM 把使用者確認的**具體案例與邊界**增補到本文件的允許案例；完成記錄後再核對第 6 項，確認全部條件符合才套用小改分類。必要條件有任何不符仍是一般功能；若要修改必要條件，須由使用者明確確認修改規則本身。
- 使用者只確認單一任務時，新增案例須以該任務 ID 限定適用範圍，仍需符合全部必要條件；不能自動推廣成整類允許。要成為通用案例，須有使用者對該類條件的明確同意。
- PM 更新本文件並引用當次規劃書／PR，記下日期、原分類及原因、使用者確認內容、適用條件、排除條件與驗證方式。RD 不自行增補或放寬。
- 未確認的候選案例仍走一般功能。先累積實際任務，不為預想案例增加新等級或打分制度。
