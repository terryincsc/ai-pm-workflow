# 規劃書、範圍與派工紀錄

每次已立案需求由 PM 撰寫一份 `NNN_YYYY-MM-DD_大綱.md`；編號取現有最大值 + 1，日期先用 `date +%F` 查證。小改也用同一命名，可精簡內容。分類依據見 [TASK_SIZING.md](../TASK_SIZING.md)。

## 由誰寫、何時寫

- PM 在實作前撰寫正式規格、範圍、驗收與回歸要求，取得使用者確認；既有授權不重複詢問。
- 技術不明時，PM 可先派唯讀 rd_architect 查檔案與 commit。RD 回報證據、推論與未知事項，不代替 PM 決定產品範圍。
- PM 在每次派工前填入派工紀錄；完成、受阻、退回或升級模型時更新。各作者提供成果與指令證據，不一起改這張表。
- 開 PR 前寫驗收結果及「✅ 實作與驗證完成，待合併」。實際合併以 PR 狀態為準。

## 範圍清單（一般功能逐項填；不適用也註明）

| 項目 | 要寫清楚什麼 |
|---|---|
| 使用者與情境 | 哪些角色、入口、前置條件與操作情境適用 |
| 預期行為與例外 | 輸入、輸出、狀態轉移、錯誤情況；可觀察結果，不寫「正常即可」 |
| 既有行為 | 哪些原有行為必須維持，列受影響的回歸情境與依據 |
| 修改邊界 | 可改檔案／模組／介面；明確禁止碰的內容；每個檔案由誰負責 |
| 資料邊界 | 新資料／既有資料、讀／寫、目標環境及資料範圍；無資料處理就註明 |
| 永久與一次性 | 長期行為與一次性處理分列；腳本撰寫和真實資料執行分開授權 |
| 本次不做 | 容易被誤加的 UI、API、排程、通用工具、相鄰功能 |
| 驗收與回歸 | 每項需求 ID 對應正常／邊界／失敗案例、預期結果、驗證方式及證據；哪些未測、為何 |

例如：「新增菜單的食物不要求甜度／冰塊；既有菜單只在已確認資料範圍做一次性修正；飲料規則維持；不新增批次管理介面。」PM 依此寫驗收，RD 補充涉及檔案、資料關係與風險。不能只寫「修正客製設定」。

## 規劃書建議結構

1. 已確認需求與來源、分類及理由（小改附案例 ID）、風險標記。
2. 上述範圍清單、驗收／回歸表、未決事項及對策。
3. RD / Test Writer 任務拆分、介面契約、檔案權責、平行工作隔離與整合順序。
4. PM 派工與驗證紀錄；省略角色的理由。
5. 審查、驗證證據、限制與最終狀態。

## PM 派工與驗證紀錄範本

| 派工 ID | 角色／平台／實際模型／effort | 選擇理由 | 輸入規格及版本 | 可動／禁止檔案與整合安排 | 狀態與結果證據 |
|---|---|---|---|---|---|
| W1 | rd／… | … | 需求 ID／plan／base commit | … | 待派工；回報後填指令、輸出重點、限制 |
| W2 | test_writer／… | … | 相同規格／介面契約 | … | … |
| W3 | reviewer／… | 獨立審查 | 整合版本／diff | 唯讀、不跑測試 | 問題、分級及處理 |
| W4 | tester／… | 獨立驗收 | 審查通過的整合版本 | 不改來源檔 | 需求→測試→結果／證據 |

派工時記錄「要求模型」；平台有回報再記「實際模型」，無法查證就明寫未確認。effort 不支援或未指定也明寫。另記總退回次數（最多兩次）、升級原因、缺陷／漏測；耗時、token、成本只記工具實際提供的數據，不估造。
