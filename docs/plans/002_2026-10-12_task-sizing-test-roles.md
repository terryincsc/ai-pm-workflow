# 002 — 小改條件、唯讀分析與測試分工

日期：2026-10-12。使用者已在對話確認本次調整，依既有授權開工。

## 需求與範圍

- R1：只有符合已列條件的任務才是小改；其餘一律一般功能，不設第三種複雜流程。試行後由使用者確認具體案例，PM 才增補 Markdown 規則。
- R2：需求分析及範圍規劃可先派 rd_architect 唯讀檔案與 commit；RD 提供證據，PM 撰寫正式範圍、驗收及回歸要求。
- R3：分開 test_writer 與 tester；前者撰寫測試，後者由 PM 在整合與審查通過後另開全新上下文驗收。兩平台提供明確模型預設。
- R4：PM 在本規劃書維護派工與驗證紀錄，從派工前開始，隨回報更新。
- 永久行為：更新模板流程、角色文件、兩平台設定及相關說明。
- 一次性處理：無。同步 PR #4 已合併、遠端已更名 ai-pm-workflow 的現況。
- 可動：AGENTS.md、README.md、docs/、兩平台 agents 設定。
- 不做：產品程式碼、執行引擎、自動模型路由、付費模型實測、遠端合併。
- 保留：使用者確認範圍、獨立審查與驗收、最多退回兩次、一需求一分支一 PR、使用者 merge、一次性資料處理授權。

## 分類、角色與驗收

本次修改流程政策與新增角色，不符合小改條件，走一般功能。純文件／設定工作不需要撰寫持久測試程式，因此不派 test_writer；PM 修改流程文件，Reviewer 唯讀審查，Tester 靜態驗證。

| 需求 | 驗收方式 |
|---|---|
| R1 | TASK_SIZING 有必要條件、明確案例、預設一般功能、使用者確認後才擴充 |
| R2 | 分析可在實作核准前執行但不能寫檔／跑測試；PM 擁有正式規格；範圍清單完整 |
| R3 | 七種角色兩平台可解析且映射一致；test_writer 只寫指定測試；新 tester 獨立驗收 |
| R4 | 紀錄模板含分類、角色、模型、檔案權責、回報與證據，PM 全程維護 |
| 回歸 | 共用入口、角色作用範圍、授權、退回上限、PR 規則及原一次性處理規則保留 |

風險：各文件流程互相矛盾、平行寫檔衝突、測試依實作倒推預期。對策：獨立一致性審查、明確檔案權責、從核准規格設計測試。實際 CLI 載入與模型呼叫不在本次驗證內。
