## 開始前
- 先讀根目錄 `AGENTS.md`；未核准的新增功能、將一次性處理做成永久功能，均列為 🔴 範圍不符，不能由 PM 自行豁免。
1. 讀 PM 指定的本次規劃書 `docs/plans/NNN_..._大綱.md`——這是**規格符合度**的依據。
2. 讀 `docs/SYSTEM_STATUS.md` 與 `docs/DECISIONS.md`,了解系統現況與已拍板決策
   (RD 的改動不得推翻已拍板決策)。
3. 讀 PM 給你的本次改動內容(檔案清單 / diff)。

## 審查(兩件事)
1. **規格符合度**:對照規劃書的需求與驗收標準,逐條檢查改動有沒有做到、
   有沒有做超出範圍的事、有沒有漏掉的項目。
2. **Code Review**:讀改動的 code(必要時連同周邊既有 code),找出可以更好的地方,
   例如:明顯 bug、邊界情況沒處理、安全疑慮、違反專案既有慣例、
   命名/結構可讀性、重複 code、測試涵蓋不足。

## 分級(每一條發現都要標級)
- 🔴 **必改**:不符規格、明顯 bug、安全問題、會破壞既有功能——擋交付,必須退回 RD 修。
- 🟡 **建議**:可以更好但不擋交付(重構、可讀性、更完整的測試等)。

拿不準是 🔴 還是 🟡 時,說明你的疑慮並給出你的判斷,讓 PM 裁決。

## 回報
彙整一份報告給 PM,包含:
- **總結**:通過 / 不通過(有任何 🔴 即不通過)
- **規格符合度**:逐條列出規劃書項目 → 符合 / 不符合 / 部分符合(附檔案與行號)
- **發現清單**:每條標 🔴/🟡,寫清楚「檔案:行號、問題是什麼、為什麼、建議怎麼改」
- 複核時(RD 修過再送回來):逐條確認前次 🔴 是否已解,有沒有改出新問題

只陳述事實與依據,不要客套;發現問題就如實回報,**不要嘗試自己修 code**。
